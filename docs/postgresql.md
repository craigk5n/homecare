# PostgreSQL support (HC-250)

HomeCare runs on PostgreSQL as an alternative to MySQL. MySQL stays the
default and nothing changes for existing installs; PostgreSQL is opt-in
through `includes/settings.php`.

Tested with PostgreSQL 17 (CI uses the `postgres:17` image). Any
PostgreSQL 12 or newer should work (identity columns,
`EXECUTE FUNCTION` triggers).

## Requirements

- PHP extensions **`pgsql`** (pages, via `includes/dbi4php.php`) and
  **`pdo_pgsql`** (`bin/migrate.php`, the test suite).
- A UTF8 database and a role that owns it:

  ```bash
  createuser -P homecare
  createdb -E UTF8 -O homecare homecare
  ```

## settings.php

```
db_type: postgresql
db_host: localhost
db_database: homecare
db_login: homecare
db_password: secret
db_persistent: false
```

- `db_host` may include a port: `db.example.lan:5433`. Use `none` for a
  local Unix-socket connection.
- The session `TimeZone` is set to PHP's default time zone on connect,
  so `CURRENT_TIMESTAMP` column defaults agree with times computed in
  PHP (on MySQL the same holds because server and PHP share the host).

## Loading the schema

Either let the migration runner do it. On an empty database it loads
`tables-postgres.sql` first:

```bash
php bin/migrate.php --dry-run   # "Empty database: would load tables-postgres.sql."
php bin/migrate.php             # loads the schema, then applies migrations/pgsql/*
```

Or load it by hand:

```bash
psql -d homecare -f tables-postgres.sql
```

Seed the starter admin user (login `admin` / password `admin`; rotate
it on first login). This is the PostgreSQL form of
`migrations/004_seed_admin_user.sql`:

```sql
INSERT INTO hc_user (login, passwd, firstname, lastname, email, is_admin, role, enabled)
VALUES ('admin', '$2y$10$sYf/R7ev6nWCEip0bEBK3.Nl.qC4sb9okTA/2qhspHHdRVYfwVIL2',
        'Home', 'Admin', 'admin@example.com', 'Y', 'admin', 'Y')
ON CONFLICT (login) DO NOTHING;
```

## Migrations

`migrations/*.sql` are written in MySQL dialect (`MODIFY COLUMN`,
`INSERT IGNORE`, `ENGINE=`...) and are **not** used on PostgreSQL.
`tables-postgres.sql` is the baseline: the full schema equivalent to
`tables-mysql.sql` after migrations 001-035. Later schema changes get a
PostgreSQL twin in `migrations/pgsql/` with the same file name.

`bin/migrate.php` with `db_type: postgresql`:

1. loads `tables-postgres.sql` if `hc_config` does not exist yet;
2. applies every `migrations/pgsql/*.sql` not recorded in
   `hc_migrations` (natural sort order), each in one transaction
   together with its `hc_migrations` row, so a failing migration leaves
   no partial DDL behind.

When adding a migration, also fold the change into `tables-postgres.sql`
and add the file name to the `INSERT INTO hc_migrations` list at the end
of that file (see `migrations/pgsql/README.md`).

## Schema differences from MySQL

| MySQL | PostgreSQL | Why |
|---|---|---|
| `INT AUTO_INCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | explicit ids still insertable; ids read back via `lastval()` |
| `DATETIME` | `TIMESTAMP(0)` | whole seconds, so values read back as `YYYY-MM-DD HH:MM:SS` like MySQL |
| `BOOLEAN`, `TINYINT(1)` | `SMALLINT` | the code compares and binds `1`/`0`; a PG `boolean` rejects `= 1` and reads back as `t`/`f` |
| `CHAR(1)` `'Y'`/`'N'` flags | unchanged | |
| `ON UPDATE CURRENT_TIMESTAMP` | `BEFORE UPDATE` trigger `hc_set_updated_at()` | `hc_patients`, `hc_medicines` |
| — | `hc_api_rate_limit`, `hc_migrations` included | `tables-mysql.sql` lacks the former (migration 010) |

## How the code stays portable

- Queries are written in the SQL subset MySQL 8, PostgreSQL and SQLite
  share. Dates are computed in PHP and bound as parameters instead of
  `NOW()`/`CURDATE()`/`DATE_SUB()` where an expression was needed;
  `CURRENT_DATE` is used where a bare "today" suffices.
- The few unavoidable differences go through
  `HomeCare\Database\Dialect` (`DatabaseInterface::dialect()`):
  `caseInsensitiveLike()` (`ILIKE` on PostgreSQL) and `groupConcat()`
  (`STRING_AGG` on PostgreSQL).
- `dbi_execute()` binds parameters server-side with
  `pg_query_params()`; `dbi_insert_id()` returns the new id on every
  driver (`lastval()` on PostgreSQL).

## Running the tests against PostgreSQL

The default suite uses in-memory SQLite. To run it against PostgreSQL:

```bash
export HOMECARE_TEST_DB=pgsql
export HOMECARE_TEST_PG_DSN='pgsql:host=127.0.0.1;port=5432;dbname=homecare_test'
export HOMECARE_TEST_PG_USER=postgres
export HOMECARE_TEST_PG_PASSWORD=
composer test
```

The tests use (and drop/re-create) only the `hc_phpunit` schema in that
database; still, point them at a throwaway database. A test server with
`-c fsync=off -c synchronous_commit=off` runs the suite several times
faster.

## Docker

The image includes `pgsql` + `pdo_pgsql`. Set these environment variables
on the web container:

```
HC_DB_TYPE=postgresql
HC_DB_HOST=postgres        # service name
HC_DB_PORT=5432
HC_DB_NAME=homecare
HC_DB_USER=homecare
HC_DB_PASSWORD=...
```

On start the entrypoint writes `db_host: host:port` into `settings.php`,
waits until the app user can connect (via PHP's `pdo_pgsql`, so no client
package is needed), then runs `php bin/migrate.php`. On an empty database
that loads `tables-postgres.sql`; afterwards it applies any pending
`migrations/pgsql/*.sql`. Running it on every start is safe, so upgrades
pick up new migrations automatically. No admin user is seeded on
PostgreSQL. Create one, or use reverse-proxy mode.

The bundled Compose stack still uses MySQL; a `postgres:17` service in a
Compose override would be the PostgreSQL equivalent.

## Known limitations

- **Case-sensitive comparisons.** MySQL's default `*_ci` collations make
  `=` case-insensitive; PostgreSQL (like SQLite) does not. Searches use
  `ILIKE` and email lookups use `LOWER()`, but e.g. logins must be typed
  with the stored case.
- **Strict typing.** PostgreSQL rejects what MySQL silently coerces, e.g.
  an empty string bound against an integer column. The pages were
  smoke-tested, but rarely used paths may still surface such errors.
- **NULL ordering.** `ORDER BY x` puts NULLs last on PostgreSQL and first
  on MySQL.
- **MySQL-only tooling:** `dump.sh` (`mysqldump`),
  `bin/seed_e2e_fixtures.php` and the Playwright E2E workflow, and the
  Docker stack (above).
- **Moving existing data** from MySQL to PostgreSQL is not automated. A
  tool such as [pgloader](https://pgloader.io/) into a database
  initialised from `tables-postgres.sql` should work; afterwards reset
  the identity sequences, e.g.
  `SELECT setval(pg_get_serial_sequence('hc_patients', 'id'), MAX(id)) FROM hc_patients;`.
